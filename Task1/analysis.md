# Задание 1. Анализ безопасности системы «Медикаменте"

## 1. Инвентаризация конфиденциальных данных

На основании описания компании выделены следующие категории данных, которые подлежат защите:

| Категория данных | Примеры | Уровень чувствительности | Системы / носители As-Is |
|---|---|---|---|
| Персональные данные (ПДн) пациентов | ФИО, дата рождения, телефон, email, адрес прописки, место работы/учёбы | Высокий | Excel, сканы (JPG/PDF), общий диск |
| Медицинские данные (PHI) | Медицинские карты, диагнозы, хронические заболевания, назначения, заключения | Критический | Excel, сканы, общий диск |
| Результаты лабораторных исследований | Анализы, результаты исследований, биоматериалы | Критический | Excel, сканы, общий диск |
| Платёжные данные | Суммы платежей, способы оплаты, чеки, бухгалтерские проводки | Высокий | 1С:Бухгалтерия, Excel, ККМ |
| Договорные данные | Договоры на оказание услуг, согласия на обработку ПДн | Высокий | Excel, сканы, общий диск |
| Персональные данные сотрудников | Паспортные данные, зарплата, кадровая информация | Высокий | 1С:Бухгалтерия, Excel |
| Коммерческие данные | Учёт ТМЦ, закупки оборудования, финансовая отчётность | Средний | 1С:Торговля и склад, Excel |
| Учётные данные | Логины, пароли, доменная аутентификация | Высокий | Active Directory, LDAP |

### Данные, не учтённые во внутренних системах

- Расширенная анкета пациента (адрес, место работы/учёбы, хронические заболевания) хранится в Excel и сканах без классификации и учёта.
- Согласия пациентов на обработку ПДн и медицинских данных не учитываются в электронном виде.
- Журнал записи к специалистам содержит ПДн и не имеет разграничения доступа.
- Данные о платежах дублируются в Excel и 1С, что создаёт неучтённые копии конфиденциальной информации.
- Результаты анализов, получаемые из лаборатории, планируются к интеграции, но сейчас не контролируются как отдельный поток PHI-данных.

## 2. Диаграммы потоков данных (DFD)

Диаграммы потоков данных разработаны в двух вариантах:

- `dfd-as-is.drawio` — текущее состояние (As-Is) для процессов:
  1. Регистрация пациента и запись на приём.
  2. Ведение медицинских карт и заключений.
  3. Приём платежей и бухгалтерский учёт.
  4. Обработка результатов лабораторных исследований.
- `dfd-to-be.drawio` — целевое состояние (To-Be) с применением механизмов защиты.

Каждый процесс представлен на отдельной странице draw.io.

## 3. Аудит мер по обеспечению безопасности данных

### Сопоставление процессов и требований

| Процесс | Требование / практика | Состояние As-Is | Проблема |
|---|---|---|---|
| Хранение ПДн и PHI | Шифрование данных at rest | Отсутствует | Данные в Excel/JPG/PDF на общем диске не шифруются |
| Передача данных между системами | Шифрование in transit (TLS) | Отсутствует | Обмен файлами по сети и через общий диск без контроля |
| Доступ к данным | RBAC / ABAC | Отсутствует | Только доменная аутентификация, нет разграничения по ролям |
| Обработка данных | Audit trail / Data Lineage | Отсутствует | Нет журналов действий с конфиденциальными данными |
| Аналитика и BI | Обезличивание / псевдонимизация | Отсутствует | Нет разделения конфиденциальных и аналитических данных |
| Интеграция с лабораторией | Безопасные API-контракты | Не реализовано | Планируется без проработанной политики доступа |
| Мобильное приложение / ЛК | Аутентификация, авторизация, маскирование | Не реализовано | Нет защищённого API для работы пациентов только со своими данными |
| Удаление данных | Политика retention / право на забвение | Отсутствует | Нет механизма удаления данных по запросу пациента |
| Резервное копирование | Резервное копирование и восстановление | Не описано | Риск потери данных при сбое единственного сервера |
| Физическая безопасность | Изоляция инфраструктуры | Недостаточна | Сервер находится в офисе, физический доступ сотрудников |

### Список проблемных зон

1. **Отсутствие классификации и тегирования данных.** Невозможно применить дифференцированную защиту, если неизвестно, какие данные где находятся.
2. **Хранение конфиденциальных данных в файлах.** Excel, JPG, PDF на общем диске доступны широкому кругу сотрудников без аудита.
3. **Дублирование данных.** Платежи ведутся одновременно в Excel и 1С, что увеличивает поверхность атаки.
4. **Отсутствие ролевой модели.** Любой авторизованный в домене сотрудник потенциально может открыть любой файл.
5. **Отсутствие шифрования.** Данные не шифруются ни при хранении, ни при передаче.
6. **Отсутствие журналов аудита.** Невозможно расследовать инциденты и доказать соответствие требованиям.
7. **1С в файловом режиме.** База данных доступна как файл на сервере, что упрощает несанкционированный доступ.
8. **Единая точка отказа.** Один физический сервер в офисе без отказоустойчивости и резервного копирования.
9. **Не подготовлена безопасная интеграция с внешними системами.** Лаборатория и будущие партнёры получат доступ к данным без политик и контроля.
10. **Отсутствие механизма управления согласиями.** Нет учёта согласий пациентов на обработку данных и отзыва согласия.

## 4. Улучшения: данные и способы защиты

| Данные | Способ защиты | Обоснование |
|---|---|---|
| ПДн пациентов (ФИО, телефон, email, адрес) | Шифрование at rest (AES-256), TLS in transit, маскирование в интерфейсах | Защита от утечки и несанкционированного просмотра |
| Медицинские карты, диагнозы, заключения | Шифрование at rest, токенизация идентификаторов, RBAC/ABAC | PHI — наиболее чувствительные данные, требуют строгого контроля |
| Результаты анализов | Шифрование at rest, передача через защищённый API, подпись/контроль целостности | Критичные медицинские данные, передаются из внешней лаборатории |
| Платёжные данные | Шифрование, токенизация номеров карт (при необходимости), аудит | Требования PCI DSS и 115-ФЗ |
| Договоры и согласия | Шифрование, электронная подпись, учёт сроков хранения | Юридическая значимость и требования 152-ФЗ |
| ПДн сотрудников | Шифрование, RBAC, аудит доступа | Защита кадровых и зарплатных данных |
| Аналитические копии данных | Обезличивание / псевдонимизация перед загрузкой в Data Lake | Использование для BI/ML без раскрытия PHI |
| Логи и аудит-события | Шифрование, контроль целостности, ограниченный доступ | Сами логи содержат чувствительную информацию |

### Обфускация и обезличивание

- **Обезличивание** применяется перед загрузкой данных в озеро данных (Data Lake) для BI, ML и AI: удаляются/хэшируются прямые идентификаторы (ФИО, телефон, email).
- **Псевдонимизация** используется в аналитических витринах: замена идентификаторов на токены с возможностью восстановления только уполномоченным сервисом.
- **Обфускация** применяется в непродукционных средах: маскирование ФИО, телефонов, адресов, диагнозов для разработки и тестирования.
- **Маскирование** в пользовательских интерфейсах: частичное скрытие телефона, email, паспортных данных в зависимости от роли.

## 5. Механизм тегирования данных

### Цели тегирования

- Автоматическое определение уровня чувствительности данных.
- Применение политик защиты на основе тегов (шифрование, маскирование, доступ).
- Контроль перемещения данных между доменами и системами.
- Поддержка аудита и compliance.

### Категории тегов

| Группа тегов | Примеры | Применение |
|---|---|---|
| Юридическая классификация | `pii`, `phi`, `payment`, `confidential`, `public` | Определение режима защиты |
| Регуляторные требования | `152-fz`, `pci-dss`, `medical-secret` | Соответствие законодательству РФ |
| Происхождение данных | `patient-portal`, `reception`, `lab`, `1c-accounting`, `1c-warehouse` | Data Lineage |
| Назначение | `production`, `analytics`, `test`, `backup` | Управление копиями данных |
| Срок хранения | `retention-1y`, `retention-5y`, `retention-75y` | Автоматическое удаление по истечении срока |
| Согласие | `consent-given`, `consent-withdrawn` | Управление обработкой данных |

### Инструмент тегирования

В качестве инструмента предлагается **Apache Atlas** (или альтернативы: OpenMetadata, DataHub, Collibra). Он позволяет:

- Создавать бизнес-глоссарий и классификации.
- Автоматически назначать теги на основе правил (например, по имени столбца, маске данных).
- Интегрироваться с Apache NiFi и хранилищами данных.
- Отслеживать происхождение данных (lineage).

### Процесс тегирования

1. **Классификация.** Администратор данных определяет классификации и политики.
2. **Автосканирование.** Сканеры Apache Atlas анализируют источники (PostgreSQL, S3, файлы) и назначают теги.
3. **Ручная верификация.** Data-стюард подтверждает или корректирует автоматически назначенные теги.
4. **Применение политик.** На основе тегов Apache Ranger (или аналог) применяет политики доступа и маскирования.
5. **Мониторинг.** Система аудита фиксирует обращения к тегированным данным и сигнализирует об аномалиях.

## 6. Инструменты, способы и меры обеспечения конфиденциальности

| Мера / инструмент | Назначение | Применение в потоках |
|---|---|---|
| **Apache NiFi** | Управление потоками данных, ETL, маршрутизация | Все потоки между системами, анонимизация перед Data Lake |
| **Apache Atlas** | Data catalog, тегирование, lineage | Все хранилища данных |
| **Apache Ranger** | Политики доступа, маскирование столбцов | БД, Data Lake, отчётность |
| **HashiCorp Vault** | Управление ключами шифрования и секретами | Шифрование at rest, API-ключи, пароли |
| **PostgreSQL + TLS** | Защищённое хранение структурированных данных | CRM, записи на приём, медицинские карты |
| **S3-совместимое хранилище (MinIO / Yandex Object Storage)** | Хранение файлов и сканов с шифрованием | Медицинские документы, договоры, результаты анализов |
| **Keycloak / Active Directory** | IAM, SSO, MFA, RBAC/ABAC | Аутентификация сотрудников и пациентов |
| **API Gateway (Kong / NGINX / Envoy)** | Контроль доступа к API, rate limiting, WAF | Портал пациентов, интеграция с лабораторией |
| **DLP-система** | Предотвращение утечек данных | Исходящий трафик, email, файловые обмены |
| **SIEM (ELK / Wazuh)** | Сбор и анализ журналов безопасности | Аудит доступа, обнаружение аномалий |
| **Backup с шифрованием** | Резервное копирование | Все критичные системы |
| **Data Loss Prevention на уровне БД** | Маскирование и аудит SQL-запросов | Аналитика, доступ разработчиков |

## 7. Рекомендации по доработке диаграмм

На диаграммах `dfd-to-be.drawio` отражены следующие улучшения:

- Все потоки между системами проходят через **API Gateway** или **Apache NiFi** с TLS.
- Конфиденциальные данные хранятся в зашифрованном виде (AES-256) в PostgreSQL и S3.
- Ключи шифрования управляются через **HashiCorp Vault**.
- Доступ к данным регулируется **Keycloak/AD + Apache Ranger** на основе RBAC/ABAC.
- Перед загрузкой в **Data Lake** данные обезличиваются/псевдонимизируются.
- Все действия с тегированными данными логируются в **SIEM**.
- Интеграция с лабораторией осуществляется через защищённый API с проверкой прав пациента.

## 8. Выводы

Текущая архитектура «Медикаменте» не соответствует требованиям безопасности конфиденциальных данных. Основные риски связаны с хранением данных в файлах, отсутствием шифрования, ролевой модели и аудита. Для перехода к целевому состоянию необходимо:

1. Внедрить классификацию и тегирование данных.
2. Централизовать хранение конфиденциальных данных в защищённых хранилищах.
3. Настроить шифрование at rest и in transit.
4. Внедрить RBAC/ABAC и аудит доступа.
5. Обеспечить безопасную интеграцию с внешними системами.
6. Построить озеро данных на обезличенных копиях.
7. Внедрить резервное копирование и политики хранения данных.
